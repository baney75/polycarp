### Added
- Agents search a long PDF or page instead of reading it whole. `get_page_text {query}` (MCP and the side panel) returns the matching pages of a PDF, best first, with their numbers and snippets, or the matching parts of a long page with the offset that reads each one; a PDF searched whole is kept while the extension runs, so the next search of it costs no second parse (a pages read parses its own range). The side panel's `extract_document` reads a long web page by URL too, as text in parts. On a 400-page Ethics, "what does Aristotle say about friendship in Book VIII" is one search and one read of two pages on a 32k model: the book never enters the context (`cli/test/e2e-panel.test.mjs`, and over MCP `cli/test/e2e-bridge.test.mjs`). Decision D44.
- Long side panel chats are summarized instead of cut. When the context guard would drop a chat's earliest turns to fit the model's window, the chat's own model writes notes on them in six fixed sections (decisions, facts with their sources, tried and failed, what it had not finished, done steps, files), and the request sends every one of the person's earlier messages word for word (long ones cut by code, marked), the notes, and the recent turns verbatim. The latest question is always sent whole, and tool calls keep their results. The notes are stored in the chat, so they hold across a reload, and the transcript shows "Earlier messages summarized" with them; `thread_read` shows them too, bounded. If the summary call fails, the panel says so once and the guard cuts as before. Page text reaches the summarizer as untrusted data. Decision D45; tests in `test/compaction.test.mjs` and the panel e2e.
- The side panel's model now reads pages and acts by ref with the same tools outside agents use. Five native tools: `read_page`, `find` and `get_page_text` see the current tab with refs, `act` clicks, types, fills, presses, hovers, scrolls, drags, waits, takes screenshots or runs a batch of steps, and `handle_dialog` answers a dialog. They run the bridge's own handlers in the service worker (one implementation with MCP: stale refs refused, clicks hit-tested, shadow roots and frames reached), keep the panel's reach (its own tabs, never a Polycarp page, no site opened) and get step labels such as "Click e5" and "Type "hi" in e2". The system prompt teaches the loop (read, act by ref, read again; refs expire when the page changes) and the REPL runs code (data work, skills, recorded workflows' replay(), skill code under test) while the model's own clicks and keys go through `act`. Stop ends a page tool call at once, and the screenshot scale and open dialogs outlive a service worker restart (act x/y with no screenshot is refused, not guessed). The ten input tools are one `act` tool to save tokens: the panel's prompt and tools grow 1,187 tokens (+13%), not 1,938 for separate tools (docs/benchmarks.md). `polycarp mcp --profile panel` serves the same tools for the benchmarks, and `perception.mjs` and `web-bench.mjs` take `--stack panel`. - `remote test` proves an assistant can reach the connector, from outside, and `remote fix` repairs it with one command. `remote test [--json]` asks public DNS over HTTPS for the name and connects to that public address with the name as TLS SNI and Host, so a ts.net name is never answered from inside your tailnet. It checks, each ok, warn or fail with one next step: public DNS, the certificate, the protected-resource and authorization-server metadata, a 401 sign-in challenge naming the metadata, and a streaming probe whose first bytes must arrive within 5 seconds (a buffering proxy or quick tunnel fails it). The probe's token is made in process with the narrowest scope (`skills.read`, no browser access), used once, and deleted in a `finally` and on Ctrl-C or SIGTERM; it is never printed, logged or in `--json`. Exit 0 ok, 1 a check failed, 2 usage, 3 not set up. `remote setup` now ends with the same checks, and a connector that answers from outside but can't stream or sign in fails setup (exit 1, `code` the check's name, `checks` in the JSON). `remote status` adds a `public test` line pointing to `remote test` when its own fetch could have stayed inside the tailnet, and its Cloudflare line now asks launchd or systemd whether the tunnel's service runs instead of trusting the file. `remote fix [--yes] [--dry-run] [--json]` makes one repair per fault in a fixed order, checking again after each: download the pinned cloudflared (on a yes), rewrite `remote.json` for a renamed computer (printing the old and new URL, `oldUrl` and `newUrl` in JSON), restart serve's service, restart the tunnel's service, open Funnel; then it runs the outside proof. It names, with the exact command, what only you can do (`loginctl enable-linger`, `sudo tailscale set --operator=$USER`, `token passcode`, `remote setup`) and never deletes or overwrites a DNS record, runs sudo, touches Tailnet Lock, turns a route off, or revokes a token or connector. In a terminal it asks before each step; with no terminal and no `--yes` it changes nothing and exits 3 with the list. `docs/remote.md` now starts with a quick start, per-platform notes and a troubleshooting table keyed by `state` and check name. Tests: `cli/test/remote-proof.test.mjs`, `cli/test/remote-fix.test.mjs`.
- `remote test` and `remote setup` review follow-ups (PR 130). Setup's final proof waits only on a failure marked `pending` (no public address yet, or a timeout or refusal); a refused certificate, a 421, another connector's metadata or a failed DNS lookup fails setup with that check's code, and every failure after `remote.json` is saved reports `connectorUrl`. A `--public-url` that is a private address literal warns instead. Every request has an absolute deadline, so trickled headers can't stretch the 5-second stream limit. The probe token expires two minutes after it is made, enforced wherever tokens are checked (`expiresAt`; `token list` shows `expired`), and a delete that fails adds a `probe_cleanup` failure naming its id. `auth_metadata` requires an authorization and token endpoint, and any registration endpoint, on the connector's own origin. TLS failures are sorted by code (certificate, not HTTPS, unreachable, refused). DoH answers with an HTTP error or a SERVFAIL are failures, and a name with no A record is looked up as AAAA. A Cloudflare Secondary DNS zone passes the zone check. `token-usage.json` is written atomically and drops ids with no token. Setup names `install --browser <name>` as the launcher step. The test seams moved out of the environment into a module the tests preload (`cli/test/helpers/remote-test-hooks.mjs`).
- Remote access now works on Windows, through Tailscale or Cloudflare, without administrator rights. `polycarp browser remote setup` makes each service (serve, the Cloudflare tunnel, hub, link) a Task Scheduler task for your account alone, made from XML with `schtasks` (`/Create /XML`, `/Run`, `/End`, `/Delete`): it starts at your logon with limited rights and no stored password, and runs a script in `services\` under the helper's config folder that sets the folders, appends output to `logs\<name>.log` and starts the program again after 10 seconds. The scripts name no folder (they find it from their own place, so a non-ASCII profile works), and a log past 10 MB becomes `<name>.log.1` when the program starts again. `remote off`, and setup run again, end the program each task started by the pid it records (`taskkill /T`), only while `Get-Process` reports the start time it recorded, confirm with `tasklist` that it is gone, then delete or replace the task; a program that exited leaves an `exited` record, a record whose process is gone or is now another one counts as stopped, and a running task with no record, or a start time that can't be read, keeps the task and says what to end. The guided setup opens the Funnel page on Windows through `rundll32.exe url.dll,FileProtocolHandler` and names Tailscale's Start menu entry for sign-in. A path a task can't run safely (a quote, `%`, `^` or a line break) and a refused task (in any language) fail with what to do; nothing asks for elevation. Polycarp's own cloudflared now has the pinned release's `cloudflared-windows-amd64.exe` with GitHub's SHA-256 (no Windows on Arm build ships), installed as `bin\cloudflared.exe` after the check. `tailscale.exe` and `cloudflared.exe` are found on PATH, then in their installers' Program Files folders (`cli/src/tool-paths.ts`). macOS and Linux are unchanged, which tests check against the exact plist and unit text. Guide: `docs/remote.md`, "Windows". Tests: `cli/test/windows-service.test.mjs`.

- Agents can upload a file from your computer to a page and save a page's files back. One new MCP tool, `files`: `upload` puts local files on a file input or drops them on a drop area, `download` saves a URL or a link by ref (fetched in the page with its sign-in, 50 MB at most), `save_pdf` saves the page as a PDF, and `list`, `read`, `remove` manage what the session saved in `~/.config/polycarp/browser/files/<session>` (private: 0700, files 0600, never overwritten). A file inside the agent's project folders or its saved files uploads without a question. Any other path asks you each time, in the agent's own prompt or in the side panel under Settings > Agents, naming the agent, the file, its size and the site; the answer is never remembered, and no answer is a no. Credential-like files (`.env`, keys, `.ssh`, `.aws`, browser profiles, Polycarp's own settings) are refused wherever they are, as are links to them, hard-linked files, and anything over 10 files or 10 MB in one upload. Files only go to a site you have allowed for agents. The browser never sees a path on your computer: the helper reads the file and sends its content in pieces, checked by size and SHA-256 on both ends. A question about a file outside the project shows the file's full path in the agent's prompt. A session's saved files are removed when the session ends (`session_end`, or a remote session closing), and all sessions together keep at most 2 GB. No new browser permission. Downloads a click starts in the browser are not captured yet (D38).

- Browser sessions no longer lose tabs when the side panel and the service worker write the session table at once.
