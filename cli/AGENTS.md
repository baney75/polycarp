# The polycarp command

Done: `cargo test && cargo clippy --all-targets -- -D warnings && cargo fmt --check`.

Rules:

- Hand off exactly: arguments, input, output and exit code stay what the tool gave. On Unix the process is replaced.
- `polycarp browser` runs the helper inside Polycarp.app (`Contents/Resources/browser/polycarp-browser`, in `~/Applications` then `/Applications`) first, after only the `POLYCARP_BROWSER_BIN` override and before `PATH`; then `polycarp-browser` on `PATH` (it also runs under that name, so `ps` shows it), and `tabkyra` on `PATH` and its older spots as the fallback for installs made before the rename. The `bundled` list on `Tool` holds those spots.
- Nothing runs through a shell.
- Nothing runs from inside the current folder's tree. Every candidate passes `check()`, whether it came from an override, `PATH` or a fixed spot. It must be an absolute path and not under the current folder (`$PWD/node_modules/.bin` counts), including through a symlink. Two narrow exceptions: from `/` nothing is refused, so the system spots work; and when the current folder is the home folder or an ancestor of it, a candidate in a specific per-user install place is still allowed (`HOME_ALLOWED` in `main.rs`: `~/.local/bin`, `~/.local/lib/node_modules`, `~/.local/share/mise`, `~/.cargo/bin`, `~/.bun/bin`, `~/.bun/install/global`, `~/.volta/bin`, `~/.nvm/versions`, `~/.asdf/shims`, `~/.asdf/installs`, `~/.npm-global`, `~/Library/pnpm`, `~/.config/tabkyra`, the Windows `AppData/Local/Programs` and `scoop` folders, and a real app bundle in `~/Applications`, only under `Contents/`). Whole trees such as `~/.local` are not listed, since a repo can be cloned into them. The home folder is checked first; `/opt` and `/usr` apply only to candidates outside it. Both the candidate's target and the folder it sits in are judged; an app bundle is judged by itself only. Everything else under the current folder is refused, including `~/node_modules/.bin`, a file directly in `~` and anything in a project folder. If the current folder, or the candidate, can't be resolved, the answer is no. A refusal for being in the current folder is said so, with the path, and still exits 127.
- Nothing runs through a shell, so on Windows a `.cmd` or `.bat` (an override, or `tabkyra.cmd` from npm) is refused with the reason, and `doctor` calls it present but not runnable.
- On a Mac, `voice` and `doctor` use the same app: `/Applications/Silas.app`, else `~/Applications/Silas.app`.
- `doctor` gives each `--version` 10 seconds, reading its output included, and stops printing on a write error (a closed pipe is a quiet end) but still finishes the checks, so the exit code stays true.
- Test hooks, never set in real use: `POLYCARP_NO_SYSTEM_SPOTS`, `POLYCARP_DOCTOR_LIMIT_MS`, `POLYCARP_SHIM_CHECK` (applies the `.cmd` rule on any system), `POLYCARP_OPEN_BIN` (stands in for macOS `open`, so tests launch no app; it passes `check()` too), `POLYCARP_TEST_SYSTEM_ALLOWED` (replaces `/opt` and `/usr`).
- `version`, `doctor` and `update` never run the spaces command or the voice app to learn their build: the app's is read from `Contents/Info.plist`, a Linux `baneyspaces` from the `polycarp-build|v1|...|end|` text inside the file. Only the browser helper is asked (`version --json`, then `status --json`), under `doctor`'s time limit: `status` gets one and a half limits, and each browser 0.8 of one through `POLYCARP_BROWSER_QUERY_MS`. A part that did not answer is `Found::Unanswered` ("no answer in time"): never a mismatch, never missing, `version --check` exits 75 for it, and it never fails `update`, except that an extension whose last report during the reload step was an old build must report the new one by the end (second-F7 of the review of PR 244). The `polycarp` command that is compared is the installed one (`~/.local/bin/polycarp`), read from the `POLYCARP_BUILD_STAMP` text `build.rs` puts in the binary; on Windows it is the running one.
- `update` builds its steps as data first (`update::plan`, a pure function of `Facts` and `Options`) and runs them through a `Runner`. Tests use a fake runner and temp folders; no test runs a real step. Only `origin/main` is installed, from the clean copy under the cache folder; every build step runs inside it, and an install step there or in the folder the browser part was installed into (`nothing_is_ever_built_outside_the_clean_copy`). Every build comes before the first install, and the step that replaces the `polycarp` command is the last install. The plan then ends in one `Role::Handoff` step, `~/.local/bin/polycarp update --finish --source <checkout>`: the installed command makes its own last steps (`finish_steps`: reload, restart, final check), so the command that started the update never runs anything after it was replaced (`the_installed_command_finishes_the_update_not_the_one_that_started_it`). Four forms are for the plan alone and are not in the usage text: `update --finish`, `update --is-current <dir> <rev> [--needs a,b] [--after-install] [--wait N]` (the gate and the final check; a browser still on the old build is "reload pending", never "up to date"), `update --reload-wait <dir> <rev> [--wait N] -- <reload command>` (reloads, waits up to N seconds, and at least 4 s after each reload, for every extension that reports a build to report `<rev>`, fails when one whose last report, the look before the reload included, was an old build does not report it by the end, ends when no browser connects within 4 s, but waits up to 40 s for a browser the helper's `status --json` lists as `running` (a live `SingletonLock`, a current host manifest and the extension on in a profile's Preferences) before it reloads it, reloads once more after half the time only for one still on an old build, passes the helper's 75 through, and starts its reload command through the steps' `Runner`, so the program is found the same way) and `update --place-browser <from> <to> <link>` (Linux: copies the built helper and extension out of the cache). Mac: the app holds every part. Linux: nothing installed may point into the cache (`linux_installs_the_browser_outside_the_cache`). Windows: `plan` refuses with exit 2 for every option, `--finish` included (`windows_is_refused_with_the_build_steps`). Never run `polycarp update` without `--dry-run` as a check.
- More test hooks: `POLYCARP_CACHE_DIR` (where the clean copy goes), `POLYCARP_BUILD_COMMIT`, `POLYCARP_BUILD_DATE` and `POLYCARP_BUILD_DIRTY` (at build time, replace what git says).
- Tests get their own home and `PATH`. They never reach a real installed tool.
