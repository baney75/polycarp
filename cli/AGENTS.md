# The polycarp command

Done: `cargo test && cargo clippy --all-targets -- -D warnings && cargo fmt --check`.

Rules:

- Hand off exactly: arguments, input, output and exit code stay what the tool gave. On Unix the process is replaced.
- `polycarp browser` (`src/browser/`, Mac, and `src/browser_windows.rs`, which on Windows only checks a release with `install --dry-run`; rules in `../browser/AGENTS.md`) makes, updates and removes Polycarp Browser. Words it doesn't know run nothing: they are the old agent browser's, so it prints that the agent browser extension was removed from Polycarp, to stderr, and exits 2, as does all of it on Linux and `polycarp features on|off browser`. A PR that brings the old browser helper, agent extension or MCP server back here is refused. Its tests never read a real browser profile, keychain or release.
- `features` changes nothing: Polycarp has no parts to choose, so it prints one line (`features::ALWAYS_ON`), writes no file and exits 0, or 2 with that line on stderr for anything it can't do. It is not in `--help`.
- `update --retire-old-browser` (`retire.rs`, run by `install-app.sh` on every Mac install) retires the launchd jobs the browser left behind, booting each out and removing its plist. The remote connector's jobs (`com.polycarp.serve`, `.cloudflared`, `.hub`, `.link`) may still be live, running shims that exec node outside the app, so each goes only when the Polycarp program it runs is gone from disk; otherwise they keep running and the step prints "Your remote connector still runs on the old browser helper, outside Polycarp, so its jobs were left running; to stop one, run `launchctl bootout gui/$(id -u)/<label>` and delete its plist from ~/Library/LaunchAgents." once. `com.polycarp.browser` and `com.tabkyra.*` go only when their program is inside a `Polycarp.app` or a removed Polycarp path, directly or through a launcher that execs it. A plist whose job launchd would not let go of is kept. It never touches any other label, `com.baney.polycarp` among them, counts only plists directly in LaunchAgents (one moved to `retired-tabkyra/` stays), passes when a job is already booted out, and never deletes `~/.config/polycarp/browser/` or `~/.config/tabkyra/`. Tests use a fixture LaunchAgents folder and a stub `launchctl` (`POLYCARP_LAUNCHCTL`); never run the real bootout as a check.
- Nothing runs through a shell.
- Nothing runs from inside the current folder's tree. Every candidate passes `check()`, whether it came from an override, `PATH` or a fixed spot. It must be an absolute path and not under the current folder (`$PWD/node_modules/.bin` counts), including through a symlink. Two narrow exceptions: from `/` nothing is refused, so the system spots work; and when the current folder is the home folder or an ancestor of it, a candidate in a specific per-user install place is still allowed (`HOME_ALLOWED` in `main.rs`: `~/.local/bin`, `~/.local/lib/node_modules`, `~/.local/share/mise/shims` and `installs`, `~/.local/share/pnpm`, `~/.local/share/pipx/venvs`, `~/.local/share/uv/tools`, `~/.cargo/bin`, `~/.bun/bin`, `~/.bun/install/global`, `~/.volta/bin`, `~/.nvm/versions`, `~/.asdf/shims`, `~/.asdf/installs`, `~/.npm-global/bin` and `lib/node_modules`, `~/Library/pnpm`, the Windows `AppData/Local/Programs`, `scoop/shims` and `scoop/apps` folders, and a real app bundle in `~/Applications`, only under `Contents/`). Whole trees such as `~/.local` are not listed, since a repo can be cloned into them. The home folder is checked first; `/opt` and `/usr` apply only to candidates outside it. Both the candidate's target and the folder it sits in are judged; an app bundle is judged by itself only. Everything else under the current folder is refused, including `~/node_modules/.bin`, a file directly in `~` and anything in a project folder. If the current folder, or the candidate, can't be resolved, the answer is no. A refusal for being in the current folder is said so, with the path, and still exits 127.
- Nothing runs through a shell, so on Windows a `.cmd` or `.bat` (an override, or a `.cmd` shim from npm) is refused with the reason, and `doctor` calls it present but not runnable.
- `voice` runs nothing. Dictation is Silas, its own app: `polycarp voice` prints one line saying so, with where to get it, to stderr and exits 1. `doctor`, `version` and `update` have no voice part.
- `doctor` runs no part: it only finds each one, and stops printing on a write error (a closed pipe is a quiet end) but still finishes the checks, so the exit code stays true.
- Test hooks, never set in real use: `POLYCARP_NO_SYSTEM_SPOTS`, `POLYCARP_SHIM_CHECK` (applies the `.cmd` rule on any system), `POLYCARP_TEST_SYSTEM_ALLOWED` (replaces `/opt` and `/usr`), `POLYCARP_TEST_WATCH_FAIL` (`files index --watch` acts as if watching failed and falls back to a rescan).
- `version`, `doctor` and `update` never run the spaces command to learn its build: the app's is read from `Contents/Info.plist`, a bare `polycarp-spaces` from the `polycarp-build|v1|...|end|` text inside the file, and the agent skill it would write from the `polycarp-skill|v1|begin|` ... `polycarp-skill|v1|end|` text inside the same file (`skill.rs` there spells the markers; `version::SKILL_BEGIN` and `SKILL_END` must match). No part is asked anything at run time, so a part is found or absent, never unanswered, and `version --check` exits only 0 or 1. The `polycarp` command that is compared is the installed one (`~/.local/bin/polycarp`), read from the `POLYCARP_BUILD_STAMP` text `build.rs` puts in the binary; on Windows it is the running one.
- `update` builds its steps as data first (`update::plan`, a pure function of `Facts` and `Options`) and runs them through a `Runner`. Tests use a fake runner and temp folders; no test runs a real step. Only `origin/main` is installed, from the clean copy under the cache folder; every build step runs inside it (`nothing_is_ever_built_outside_the_clean_copy`). Every build comes before the first install, and the step that replaces the `polycarp` command is the last install. The plan then ends in one `Role::Handoff` step, `~/.local/bin/polycarp update --finish --source <checkout>`: the installed command makes its own last step (`finish_steps`: only the final check), so the command that started the update never runs anything after it was replaced (`the_installed_command_finishes_the_update_not_the_one_that_started_it`). No step touches the browser that moved (`no_step_touches_the_browser_that_moved`). Two forms are for the plan alone and are not in the usage text: `update --finish` and `update --is-current <dir> <rev> [--needs a,b] [--after-install] [--wait N]` (the gate and the final check; an older plan's `--needs` that still names `browser helper` reads as if it did not). The final check runs from the home folder. Mac: the app holds every part. Windows: `plan` refuses with exit 2 for every option, `--finish` included (`windows_is_refused_with_the_build_steps`). Never run `polycarp update` without `--dry-run` as a check.
- More test hooks: `POLYCARP_CACHE_DIR` (where the clean copy goes), `POLYCARP_BUILD_COMMIT`, `POLYCARP_BUILD_DATE` and `POLYCARP_BUILD_DIRTY` (at build time, replace what git says).
- Tests get their own home and `PATH`. They never reach a real installed tool.
- `agent` (`src/agent/`, docs in `docs/agents.md`) is one MCP gateway; it adds reach and scopes, never a second behavior: every tool calls the same function its own command or MCP server calls. The HTTP server binds loopback only (`server::check_bind`); the tailnet listener binds Tailscale addresses only and authorizes by whois (`files::serve::authorize`) before it reads a request. Every request checks Host (loopback names, or the host of the tunnel that is set up) and refuses anything a web page sent, except GET on the metadata and the approval page; nothing sends CORS headers. Every install has local, the tailnet and its own tunnel (`policy::Route`); never build or deploy a hosted relay here. OAuth is PKCE S256 only with exact redirect matching, required `state`, one-use codes, rotating refresh tokens (a spent one coming back ends the grant), and approval only at this machine's command line; the approval page has no buttons, forms or scripts. Every secret is stored as its SHA-256 in `agent/` (0700, files 0600, written whole). Never ask for or store a Cloudflare API key; only check that `~/.cloudflared/cert.pem` exists, never read it. App tools send only the wire ops ping, list, setting, focus, agent and browser (`no_tool_sends_an_op_that_opens_a_shell_types_or_updates`); browser is tab titles and addresses under the `browser:read` scope, and the app answers it only while its Settings switch is on. Tests use a fake app link, a stub tailnet and a stub tunnel runner; no test starts a real tunnel, touches Cloudflare or Tailscale settings, or reaches a real app.
- `doctor` prints one indented line under the verdict for each part that is absent or odd (`version::fixes`, a pure function of the parts, the verdict and `version::Os`): what is wrong, then the fix for that platform. The Mac lines are tested in `version.rs`; the exit code is unchanged.
- `mail host` (`src/mail/`) is Polycarp Mail's native messaging host: the browser starts it, so it is not in `--help`. A message in is at most 64 MiB and a reply at most 1 MB. Tests feed the line bytes; none reaches a real account or server.
